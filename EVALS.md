# Оценка качества Tulpar AI Coach

Все прогоны автоматические: `evals/run.py` читает golden-наборы из `evals/golden/`, пишет результаты в `evals/results/*.json` и сводку в `evals/results/SUMMARY.md`. Таблицы ниже собирает `evals/report.py`. Модель-судья — другого семейства, чем отвечающая модель, чтобы не оценивать саму себя.

У кэша ответов, guardrails, согласия судей, озвучки и парсинга PDF свои скрипты (`evals/cache_eval.py`, `evals/guardrails_eval.py`, `evals/judge_agreement.py`, `evals/tts_bench.py`, `evals/parsing_backends.py`). Они пишут отдельные файлы в `evals/results/` и в автоматический блок «Результаты» не входят: их цифры собраны в выводах 16–21.

## Метрики и чего они не показывают

| Метрика | Что значит | Чего не показывает |
|---|---|---|
| intent accuracy | доля сообщений, отправленных в верную ветку | цену ошибки: пропустить боль хуже, чем лишний раз позвать тренера |
| escalation recall | доля опасных сообщений, ушедших тренеру; цель 100% | насколько хорош ответ самого тренера |
| false escalation rate | доля безопасных сообщений, зря ушедших тренеру | нагрузку на тренера в реальном потоке сообщений |
| hit@4, MRR | нашёлся ли ожидаемый источник среди 4 фрагментов и насколько высоко | полноту ответа: источник найден, но ответ может быть неполным |
| keyfact accuracy | есть ли в ответе ключевые факты и цифры из эталона | правильность формулировок вокруг цифр |
| faithfulness (судья, 1–5) | опирается ли ответ только на источники | правильность самих источников. Согласие судей между собой измерено (вывод 19): три судьи разных семейств на 44 ответах совпадают по pass/fail на 93,2%, их pass% различается на 2,2 п. п. Но каппа Флейса всего 0,227: почти все оценки — 5, и часть расхождений — из-за фразы «при боли скажите тренеру». Согласие с человеком ещё не измерено: выборка из 10 ответов в `evals/human/` готова, оценки в ней не проставлены |
| correctness (судья, 1–5) | совпадает ли ответ с эталоном по смыслу | качество эталона: его писал один человек. Судьи согласны между собой сильнее, чем по faithfulness: каппа Флейса 0,675 |
| correct refusal rate | доля вопросов без ответа в корпусе, переданных тренеру | вежливость отказа |
| validator exact match | совпадают ли найденные ошибки с ожидаемыми | противопоказания, которых нет в каталоге: валидатор знает только размеченные |
| draft valid (first try / final) | проходит ли черновик модели валидатор сразу и после цикла исправлений | согласен ли с черновиком тренер — это видно только по реальным решениям в очереди |
| top-1 на фото | верно ли названо главное блюдо | граммы: вес по фото не оценивается, его уточняет клиент |
| p50 / p95, токены, $ за запрос | скорость и стоимость по реальным вызовам | цену подписки Ollama Cloud: её токены посчитаны по цене аналога у Groq |
| кэш: paraphrase hit rate | доля перефразов, получивших из кэша ответ на свой вопрос | долю повторов в живом потоке: пары написаны вручную |
| кэш: ошибочные ответы | сколько ловушек получили чужой ответ (и сколько перефразов попали не на свой вопрос); цель — 0 | подмены, которых нет ни в наборе, ни в списках лексической проверки |
| guardrails: precision / recall / FPR по категориям, FPR на безобидных | ловит ли фильтр сообщения своей категории и не срабатывает ли на безобидных ловушках | реальный поток: набор писал один человек, holdout2 — прямо перед правками |
| согласие судей: каппа Коэна (pass/fail и квадратичная), каппа Флейса, альфа Криппендорфа, разброс pass% | согласны ли судьи разных семейств сверх случайного | правы ли судьи: общий перекос всех моделей виден только при сравнении с человеком |
| TTS: p50 / p95, размер MP3, длительность | сколько ждать голосовой ответ и сколько он весит | задержку с Railway до сервиса Microsoft и казахский голос: мерились только русские ответы с машины разработчика |
| парсинг PDF: доля «неподтверждённых» слов, сходство порядка слов | совпадает ли текст бэкенда с текстом других бэкендов на той же странице | истину: ошибка, общая для двух бэкендов, не видна |

При наборах в 50–70 примеров разница в 1–2 ответа статистически незначима. Выводы из A/B ниже — направление, а не доказательство. Наборы guardrails и кэша писал тот же человек, что и сами проверки, поэтому их цифры — оценка сверху.

## Эксперименты

| Эксперимент | Гипотеза | Решение по результату |
|---|---|---|
| A/B №1: реранкер вкл/выкл | реранкер поднимает MRR на вопросах на русском к английскому PDF ВОЗ и на вопросах о заменах, ценой одного вызова API | оставить реранкер, если MRR растёт, а p50 остаётся в пределах 1 с |
| A/B №2: vision-модели на 80 фото | модель с лучшим узнаванием казахской кухни не проигрывает по отказам на фото без еды | выбор основной и резервной vision-модели |
| Размер фрагмента PDF 400/800/1200 | 800 символов — баланс: 400 рвёт рекомендации ВОЗ пополам, 1200 размывает поиск | выбрать размер для индекса |
| Temperature ответа 0.0/0.2/0.7 × 3 | при 0.7 растёт разброс и падает faithfulness; 0.0 и 0.2 близки | зафиксировать temperature узла ответа |
| top_p 0.9/1.0 | при низкой temperature top_p почти не влияет | зафиксировать top_p |
| Temperature маршрутизатора 0.0/0.7 × 3 | маршрут должен быть стабилен: при 0.7 разные прогоны дают разный ответ | temperature 0 для маршрутизатора |
| max_tokens | p95 выходных токенов ответа × 1.5 даёт запас без обрезанных ответов | зафиксировать max_tokens |
| Правила без LLM против LLM-маршрутизатора | правила-заглушка ловят часть опасных сообщений, но плохо различают пограничные случаи | правила остаются страховкой при недоступности моделей |
| A/B: текстовая модель — `minimax-m3` / `gpt-oss:120b` / `glm-5.3-flash` | модель, которая ловит все эскалации, не проигрывает по верности ответов | основная и резервная текстовая модель (вывод 15) |
| A/B: бэкенд PDF — pypdfium2 / PyMuPDF / pypdf | pypdfium2 (Apache-2.0/BSD-3) извлекает тот же текст, что PyMuPDF (AGPL-3.0) | бэкенд парсинга (вывод 16) |
| Порог кэша 0,80–0,99, с лексической проверкой и без | порога 0,95 достаточно, чтобы кэш не отвечал на похожий, но другой вопрос | порог и нужна ли проверка слотов (вывод 17) |
| Судьи: gpt-oss-120b / kimi-k2.6 / deepseek-v4.1-flash, плюс повтор deepseek | итоговый pass% не зависит от того, какая модель судит | насколько доверять faithfulness и correctness (вывод 19) |

| всё | 209 | 98,6% | 0% (из 93) |

- По категориям на всех 209 строках precision 100% везде. Recall 100% у самоповреждения, чужих данных и опасных тем, 93,3% у инъекций и 97,4% у мата и оскорблений. На первом holdout recall инъекций — 2 из 4, мата и оскорблений — 6 из 7.
- Выходной фильтр: 23 из 23, включая ответы с нутриентами («кальций 500 мг», «300 мг калия»), которые раньше блокировались как доза лекарства.
- В словаре матом теперь считаются 6 слов, все 6 — настоящие ругательства.
- Среднее время проверки — 126,1 мкс на сообщение.
- Маршрутизатор не сломан. Детерминированно вердикт фильтра не изменился ни на одной из 66 строк `router.jsonl`, все 9 строк с жёстким маркером уходят по назначению до вызова модели. Живой прогон после первого раунда (`router_guardrails_check.json`): точность 98,5%, полнота эскалаций 100%, лишних эскалаций 0%. Единственная ошибка r21 — казахский вопрос о крепатуре ушёл в «другое», фильтр тут ни при чём. На слитом коде точность 100% (вывод 21).

**Решение:** gate только на dev: recall самоповреждения 100%, остальных категорий ≥ 90%, ложных срабатываний на безобидных ≤ 5%. Holdout-срезы показываются отдельно. Три оставшиеся ошибки не подгоняются: h01 («конченый» без других слов), h09 (просьба по-английски вывести инструкции) и h10 (смена роли на «юриста»). Честно о срезах: holdout2 писал тот же человек прямо перед правками, поэтому его 100% — оценка сверху. Первый holdout уже не чистый: часть его ошибок ушла вместе с правками по ревью.

**19. LLM-судье можно верить на уровне «прошёл / не прошёл», но не в тонких A/B по faithfulness.** Гипотеза: итог не зависит от того, какая модель судит. Замер: `evals/judge_agreement.py` заново оценил 44 ответа прогона `qa_text_minimax-m3.json` тремя судьями разных семейств: gpt-oss-120b (Groq), kimi-k2.6 и deepseek-v4.1-flash (Ollama Cloud). Промпты те же, что в `evals/run.py`, temperature 0. Каждый судья оценил все 44 строки по обеим метрикам.

| метрика | pass%: gpt-oss / kimi / deepseek | разброс | все трое согласны: pass/fail | все трое согласны: балл | каппа Флейса (pass) | альфа Криппендорфа: pass / шкала 1–5 |
|---|---|---|---|---|---|---|
| faithfulness | 95,5 / 97,7 / 97,7 | 2,2 п. п. | 93,2% | 79,5% | 0,227 | 0,232 / 0,19 |
| correctness | 90,9 / 93,2 / 93,2 | 2,3 п. п. | 93,2% | 68,2% | 0,675 | 0,678 / 0,796 |

- pass% почти не зависит от судьи: разброс 2,2–2,3 п. п. Спорных строк по 3 на метрику.
- По correctness во всех трёх спорных строках (q10, q45, q46) с двумя другими не согласен gpt-oss-120b. kimi и deepseek совпали по pass/fail на всех 44 строках (каппа 1,0), gpt-oss с каждым из них — на 93,2% (каппа 0,535).
- По faithfulness каппа низкая при 93,2% согласия, потому что почти все оценки — 5 (у gpt-oss 42 из 44). Средние у судей — 4,91, 4,91 и 4,82. Разница между судьями (0,09) того же порядка, что и разница между вариантами в выводах 3 и 9 (0,01–0,10).
- temperature 0 не даёт полной воспроизводимости. Повтор deepseek по correctness совпал на 44 из 44, по faithfulness балл совпал на 95,5%, pass/fail — на 97,7% (q13: 3 → 4), взвешенная каппа 0,867.
- Длина ответа. По correctness у kimi (ρ = −0,39, p = 0,01) и deepseek (ρ = −0,363, p = 0,014) длинные ответы получают оценки ниже, но на 27 необрезанных ответах связь пропадает (p = 0,42 и 0,86). Вероятная причина — обрезка ответов на 400 символах в сохранённом прогоне (17 из 44): судья не видит часть фактов. У deepseek по faithfulness на необрезанных ответах ρ = −0,473 (p = 0,01, n = 27), в повторе −0,343 (p = 0,085). В 3 из 4 оценок ниже 5 на необрезанных ответах deepseek называет причиной фразу «при боли скажите тренеру», которой нет в источниках. Всего проверено 20 корреляций без поправки на множественные сравнения, так что одно значение с p < 0,05 могло получиться случайно.

Что это значит для faithfulness: метрика годится как грубый фильтр выдумок (промпт v2 она поймала, вывод 4), но близкие конфигурации не различает. Главный источник расхождений — несогласованность промптов: `answer.v3.md` велит добавлять «при боли скажите тренеру» в ответах о противопоказаниях и разрешает эту фразу как единственное добавление от себя, а промпт судьи не говорит, как её считать. **Решение:** faithfulness сравнивается по pass/fail и только при разнице больше разброса между судьями. Следующий шаг — ручная разметка 10 ответов: `evals/human/faithfulness_sample.csv` готов, колонка оценок пустая, подсчёт — `evals/judge_agreement.py --human`. После разметки — правка промпта судьи под фразу о безопасности.

**20. Голосовые ответы: синтез не задерживает текст.** Гипотеза: edge-tts успевает озвучить ответ сразу за текстом. Замер `evals/tts_bench.py`: первые 10 ответов из `qa_jina_answer_v3.json` × 2 повтора, тот же путь, что в продукте (очистка текста для речи → маскирование ПДн → edge-tts), голос ru-RU-SvetlanaNeural, MP3 24 кГц 48 кбит/с моно. LLM не вызывается, вход воспроизводим.

Размер зависит только от текста: одинаковый текст даёт тот же MP3 до байта. Задержка зависит от сети: в первом повторе четыре вызова заняли 5,5–7,0 с, в более ранних пробах медиана была 4,9 с и 2,9 с. **Решение:** текст отправляется первым, голос — следом. **21. Финальная регрессия на слитом коде: ухудшений нет, но оценки судьи сравнивают разных судей.** Все ветки дня слиты в `main`: кэш, guardrails, парсинг на pypdfium2, голос, обратная связь, демо. Прогоны `router_final_merged.json` (один проход, без повторов) и `qa_final_merged.json` (прогон 25.09 22:25) сравнены с последними прогонами до слияния: `router_guardrails_check.json` и `qa_text_minimax-m3.json`. Конфигурация ответа та же: Jina, фрагмент 400, t 0, `minimax-m3`. Кроме парсинга PDF, сменился судья. В прошлом прогоне `evals/run.py` вызывал судью один раз, а цепочка по умолчанию начиналась с `qwen3.5:397b`, который Ollama Cloud сняла 25.09 (HTTP 410). ## Что ломает систему сейчас

- Вопросы о технике упражнений, которых нет в каталоге Tulpar: RAG честно передаёт их тренеру, но ответа клиент ждёт дольше.
- Противопоказания заполнены у 43 из 196 упражнений: для остальных валидатор не видит риска.
- Граммы по фото не оцениваются: без уточнения клиента порция берётся по умолчанию.
- Казахский язык: маршрутизатор проверен на нескольких примерах, распознавание казахской речи не измерялось отдельно.
- Лексическое сопоставление частей тела: «колено» найдётся, «мениск» — нет.
- Кэш: проверка слотов — это списки слов, а не понимание. Подмену вне списков (другое упражнение, хват, подходы или повторения, «на спине / на груди») держит только порог 0,95. Самая высокая такая пара в наборе — 0,9092 (n78), но непроверенная формулировка может дать больше. Род глагола без слова о поле («я похудела» / «я похудел») не различается. Партия flips-new писалась вместе с проверкой, это не слепой holdout.
- Guardrails — регулярные выражения. Не ловятся: «конченый» без других слов (h01), просьба по-английски вывести инструкции (h09), смена роли без слов-маркеров (h10), запрос телефона только по имени («Дай телефон Асель»: нужен NER). С перестраховкой срабатывают «Убью себя на тренировке» (уходит тренеру как самоповреждение) и «Бот, ты дурак? шучу» (отказ как на оскорбление). Жёсткие маркеры симптомов в `tulpar_ai/graph/chat.py` сверяются с сырым текстом, невидимые символы внутри симптома там не убираются. Маска ИИН закрывает в ответе любое 12-значное число. Для честной оценки нужен третий holdout от другого автора.
- Лимиты запросов (чат, демо-вход, тренерские запросы к модели) хранятся в памяти процесса: при нескольких репликах у каждой свои счётчики.
- Судья: с человеком не сравнивался, повтор делался только для deepseek. `qwen3.5:397b`, прежняя первая модель цепочки судей, снята с Ollama Cloud 25.09 (HTTP 410, `judge_agreement.json` → `summary.unavailable`). Цепочка по умолчанию в `tulpar_ai/config.py` заменена на `deepseek-v4.1-flash` → `kimi-k2.6` → `gpt-oss-120b`. После замены финальный прогон получил faithfulness и correctness для 47 из 47 отвеченных вопросов. Пропуски в прогонах 25.09 до замены (`qa_text_minimax-m3`: 29 и 34 из 44, `qa_text_gpt-oss-120b`: 8 и 24 из 38) связаны со снятой первой моделью, их средние посчитаны по части ответов.
- Черновики программы: живой прогон `draft` не перезапускался после новой проверки группы мышц (`E_MUSCLE_GROUP`), цифры вывода 5 получены без неё.
- Озвучка: замерены только русские ответы с машины разработчика. Казахский голос (kk-KZ-AigulNeural) и обрезка на 600 символах проверены только тестами с заглушкой, задержка с Railway не мерилась. «2020 г.» читается как «2020 грамм», карточка еды — «Нашёл 2 позиций».
- Парсинг: 23 слова pypdfium2 не подтверждены другими бэкендами. 14 из них — надстрочные буквы сносок, приклеенные к слову (criticala ×8, importanta ×3, conditionsb, disabilityc, paa), остальные — в основном обрывки слов (enefits, activit, uce и т. п.). Документ, удалённый из корпуса, остаётся в индексе до пересборки.
- Обратная связь: порядок отправки оценок в LangSmith гарантирован только внутри одного процесса. При выгрузке 👎 в режиме tulpar имена клиентов не маскируются, поэтому кандидатов нужно проверять вручную перед коммитом.
